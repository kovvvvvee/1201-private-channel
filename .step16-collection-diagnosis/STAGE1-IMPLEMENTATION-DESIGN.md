# Collection 阶段 1 实施前技术确认（设计稿）

基线：`Collection.jsx` 当前实现（含 LiveDiag 日志）。本轮仅设计，零代码改动。

## 一、阶段 1 修改文件与函数清单

仅 `src/pages/Collection.jsx` 一个文件，四个函数/位置：

| 位置 | 函数/代码块 | 改动性质 |
|---|---|---|
| ~L24 | chibi 预载 effect | 延后触发时机 |
| ~L176 | `createVideoForCard` | 调用时机改变（不再 +500ms 定时器） |
| ~L239 | `tryPlayIfCurrent` | 不变（保留 canplay/loadeddata 兜底） |
| ~L294 | `loadWindowMedia` | 改为优先级队列 + load 事件链式触发 |
| ~L381 | `initialPlayTimerRef` effect | **删除** +500ms 定时器，改为图片 load 后创建 video |

不新增文件、不动 CSS、不动资源。

## 二、当前流程 vs 建议流程

### 当前（并行竞争）
```
挂载 → 3图+2Q版+video(延后500ms) 全部立即并发
     → 带宽争抢，弱网下图片被 mp4 拖慢
```

### 建议（串行优先级）
```
挂载 → 仅当前卡 img.src 赋值（fetchpriority=high）
     → img 'load' 事件（或 decode 完成）
         ├─→ 相邻卡 img.src 赋值（普通优先级）
         ├─→ Q版预载 Image() ×2
         └─→ createVideoForCard(当前卡) → video 请求发出
切换 goTo(index, dir) → 同样队列：新当前卡优先 → 其滑动方向邻卡次之 → 其余延后
```

## 三、资源调度优先级设计

### 优先级队列（三级）

| 级别 | 资源 | 触发时机 | fetchpriority |
|---|---|---|---|
| P0 | 当前卡 img | 挂载/goTo 立即 | `high` |
| P1 | 滑动方向邻卡 img（goTo 的 dir 侧） | P0 load 后 ~0ms | 默认 |
| P2 | 另一侧邻卡 img、第二邻卡 img | P1 后 requestIdleCallback/setTimeout(0) | 默认 |
| P3 | Q版预载 Image() | P0 load 后 | 默认 |
| P4 | 当前 live 卡 video | P0 load 后（与 P1/P3 同批） | preload=auto（阶段1不变） |

### 关键设计点

1. **P0 不被任何东西阻塞**：当前卡 img.src 在挂载/goTo 同步赋值，不等待任何事件。
2. **链式触发用 `img.addEventListener('load', ..., {once:true})`**：若 img 已 complete（缓存命中），直接进入下一阶段，不等事件。
3. **快速滑动**：`goTo` 每次都重置队列——新当前卡立即 P0；若其 img 已在加载中（上次窗口已发起）则不重复赋值（现有 `!img.getAttribute('src')` 判断保留），只补 `fetchpriority='high'`。旧卡的 P1/P2 请求**不取消**（已发出的 HTTP 请求取消代价高于收益），但新 P0 优先级最高。
4. **防过载**：同一时刻最多 1 张 P0 + 2 张 P1/P2 在途；±2 窗口仅在 P1 完成后经 idle 回调补充，不与 P0 竞争。

## 四、视频请求时机的明确设计

### 冲突分析
- video `preload='auto'` 会持续下载全量 mp4（293–652KB）。若与首屏图片同时发起，弱网下确实会拖慢图片——**这正是当前 +500ms 想规避但未真正解决的问题**（500ms 后仍与图片下载尾段竞争）。

### 设计决策
- **video 请求在当前卡 img `load` 事件后发起**（与 P1/P3 同批，P0 已完成下载）。
- **删除 +500ms 定时器**：`createVideoForCard(0)` 从定时器改为 img load 回调触发；若 img 已 complete（热缓存），立即执行。
- **效果**：首张照片最先显示 → 视频在其后立即开始缓冲 → `canplay` 时照片已可见，视频紧随其后播放。**这正是"Live Photo 尽可能在照片显示时就已准备好播放"的实现**。
- **阶段 1 保持 `preload='auto'`**：确保 canplay 尽早；阶段 2 再评估 `metadata`。
- **滑动到 live 卡时**：`goTo` 中 `createVideoForCard(index)` 同样改为在该卡 img load 后触发（若 img 已 complete 则立即）。

### 边界情况
- img load 失败（onerror）：video 仍应发起（poster 失败不影响视频播放）——load 回调同时监听 `load` 和 `error`，任一触发即放行后续队列。
- 非 live 卡：无 video，队列在 P3 后结束。

## 五、下一张照片预加载策略

- **不扩展到 ±2**（阶段 1）：±1 已覆盖"下一次滑动"；±2 会增加 2 张图的并发/流量，在弱网下弊大于利。
- **方向性优先**：`goTo(index, dir)` 已有方向参数，`loadWindowMedia` 增加 dir 参数——顺序 `[index, index+dir, index-dir]`（环形取模），滑动方向侧的邻卡优先于另一侧。
- **快速滑动**：每次 goTo 立即将新当前卡提为 P0；已在途的旧请求不取消；新窗口的 P1/P2 在 P0 load 后补位。用户连续快滑时，最多只有"当前+方向邻+另一邻"3 张在途，不会无限堆积。
- **复用**：img 元素常驻 DOM，已加载图片滑回零请求（浏览器缓存 decoded image）。

## 六、Q版资源策略

- **可见 Q版 img**（React `<img src={getChibiImage()}>`）：保持立即渲染——它是首屏一部分，延迟反而影响体验；其体积（70–100KB）与照片相当但只 1 张，可接受。
- **预载 Image()（当前+下一张 chibi）**：从"挂载即发"改为"当前卡 img load 后"发起，与 P3 同级。下一张 chibi 的预载在 `currentIndex` 变化时重新评估，滑动后仍有 ~300ms+ 窗口期，不会拖慢主图。

## 七、阶段 2 技术边界（预先设计，本轮不实施）

### video 保留与复用
- **保留策略**：live 卡 video 不再 `cleanupVideo` 销毁，改为 `pause()` + 保留 DOM（卡片 opacity:0 时视频层不可见，无需额外隐藏）。
- **上限**：同时保留 **当前卡 + 下一张卡**两个 video；超出窗口的 live 卡 video 销毁（沿用 cleanupVideo）。4 个 live 卡最多同时驻留 2 个，内存可控。
- **滑回复用**：`goTo` 回到已保留 video 的卡片时，直接 `video.play()`（currentTime 停在暂停点，loop 视频无需归零）；不重建 DOM、不重发请求。
- **内存防护**：保留 video 上限=2；`pagehide`/组件卸载时 `cleanupAllVideos` 兜底清空。

### preload='metadata' 与可播放的区别
- `metadata`：只拉 moov/head，够渲染首帧元数据；`play()` 时浏览器自动续拉 → **首帧可能比 auto 多 1 个 RTT**，但进入时流量省 ~70%。
- 阶段 2 决策点：若阶段 1 后 Live 首播等待仍 >2s，改用 `auto`；若流量敏感场景（4G 弱网）优先 `metadata`。

## 八、预期收益与副作用

### 预期收益
- 首屏图片不被 mp4 拖慢（并发数从 6 降到 1→递增）；
- Live Photo 在照片显示后立即开始缓冲，首播等待缩短；
- 快速滑动时方向侧图片已预载，白屏减少；
- Q版不再与主图竞争。

### 可能副作用
- 串行化使**总完成时间**略增（快网下差异 <100ms，可忽略）；
- img load 事件依赖——若图片从缓存瞬时完成，load 可能早于监听器注册 → 用 `img.complete` 判断兜底；
- 微信/iOS 对 `img.decode()`/load 事件时序可能有差异 → 阶段 1 保持 `preload='auto'` 视频策略不变，降低变量。

## 九、阶段 1 测试与回滚

### 测试（沿用 diag.mjs + 新增计时）
- 本地冷/热缓存：3 图完成时间、video canplay 时间、Q版出现时间；
- Vercel Preview：同上 + `[LiveDiag]` 无新增错误；
- 真机（微信 iOS）：首进照片可见时间、Live 首播时间、滑动白屏时长。

### 回滚
- 阶段 1 为单文件改动，`git revert` 或恢复 `loadWindowMedia` 并行版即回滚；
- 每个子步骤（串行队列/方向优先/video 提前）独立可拆，便于二分定位回归。

## 十、仍待真机验证的假设（实施不依赖其成立）

- 合成器重绘缺陷（若属实，阶段 1 不解决白屏，需阶段 3 reflow 修复）；
- 微信对 video play() 的手势门控（LiveDiag 日志监控）；
- 各资源在真机 5G/弱网下的实际耗时分布。

**本轮零代码改动，等待授权后实施阶段 1。**
